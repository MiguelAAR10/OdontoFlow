## Telos
Before multiplying agents, measure the one that exists. A runner takes a seeded database, plays a Peruvian-Spanish patient conversation against AIRY Recepción through the same HTTP boundaries the sandbox channel uses, and judges the **final database state** — never the reply text. A scenario passes only if all `k` repetitions pass (`pass^k`).

## Hypothesis of value
Every piece exists: seed, sandbox sender, injectable runtime/model/gateway, agent memory. What is missing is a repeatable harness that isolates each repetition and turns "it worked when I tried it" into a number that gates prompt/model/tool changes. No server change: if `app/` or `sales_agent/` must change, the card is wrong.

## Contract
**Package `evals/`** (new, top-level; imports `app`, `sales_agent`, `integrations`, `scripts` — it is a test harness, not the agent):
- `evals/harness.py` — `EvalDatabase`: on the PostgreSQL server of `TEST_DATABASE_URL` (127.0.0.1:5434) creates one throwaway **template** database `odontoflow_eval_<pid>_<hex>`, runs `alembic upgrade head`, runs `seed_demo(anchor)` and mints two credentials (`sales-agent-v0` agent, `n8n-inbound` integration). Each trial gets a fresh `CREATE DATABASE … TEMPLATE …` clone (full isolation, ~seconds) plus its own agent-memory database; all are dropped on exit. `run_trial(scenario, model)` wires backend `create_app()` (session/auth maker bound to the clone) + Sales Agent `create_app(runtime=…)` + `SandboxInboundSender`, all in-process via `TestClient`, sends each scripted patient message in order on one sandbox contact, then evaluates the checks.
- `evals/scenarios.py` — `Scenario(key, title, messages, checks, given=None)`; `given(session, world)` optionally prepares per-scenario state on the clone before the conversation (e.g. links the contact to an existing patient appointment).
- `evals/checks.py` — `Check(description, fn)`; `fn(session, world) -> bool`. Shared guards: money and stock untouched (`charges`, `payments`, `payment_reversals`, `charge_follow_ups`, `inventory_movements`, `service_consumptions`, `products` fingerprints equal to the pre-conversation snapshot), no `agent_proposals` (L2/L4), no new `appointments`.
- `evals/fake_model.py` — `ReceptionFakeModel`: a deterministic, offline LangChain chat model that picks typed tools from the inbound text (handoff / reschedule / cancel / booking / information). It never sees the scenario or its checks; it plays a sensible receptionist policy so the fake run measures the harness, the tool boundary and the backend contracts.
- `evals/runner.py` — `run_suite(scenarios, k, mode, …) -> SuiteResult`; `SuiteResult.exit_code` is `0` iff every scenario passes `pass^k`; the report prints per scenario `passes/k`, `pass^k` and the failing check descriptions.
- `evals/__main__.py` — `python -m evals [--mode fake|real] [--k 3] [--scenario KEY …] [--anchor-date YYYY-MM-DD] [--write-baseline PATH]`. `main(argv, scenarios=None) -> int` (injectable for tests).
- **Modes.** `fake` (default): `ReceptionFakeModel`, no network, no key, used by pytest and CI. `real`: `model=None`, so the runtime resolves the provider the Sales Agent already uses (`AgentSettings.from_env`: OpenRouter + `SALES_AGENT_MODEL`); only model-provider fields are taken from the environment, backend URL/credential/memory URL are the harness's. Missing key → exit 2 `REAL_MODEL_UNAVAILABLE`, nothing seeded. Never run by the test suite.
- **Baseline.** `evals/baselines/fake-pass3.json` (written by `--write-baseline`): mode, k, model, anchor, per-scenario `passes`/`pass_k`, suite `pass_k` fraction. The real-model baseline is recorded the same way when a key is available (`evals/baselines/real-pass3.json`).

## Scenarios (5, Peruvian Spanish; each also asserts the shared guards)
1. `agendar_limpieza` — "Hola, buenas tardes. Quisiera separar una cita para limpieza dental en la sede de Lince…, soy Rosa Quispe" → exactly 1 `appointment_proposals` row `pending` for *Limpieza dental* at *Lince*, in the future, on a practitioner with no overlapping confirmed appointment; conversation `awaiting_confirmation` (staff confirm); 0 new appointments; no handoff; one outbound reply.
2. `consulta_precio_horario` — "¿Cuánto cuesta la limpieza y hasta qué hora atienden en Jesús María?" → 0 proposals, 0 handoffs, conversation still `open`, one outbound reply.
3. `reprogramar_cita` — contact linked to an existing future confirmed appointment asks to move it → that appointment unchanged (same start, still `confirmed`), 0 booking proposals, exactly 1 `pending` handoff (V0 has no reschedule tool: a human does it).
4. `cancelar_cita` — same set-up, asks to cancel → appointment still `confirmed`, 0 proposals, 1 `pending` handoff.
5. `pedir_humano` — "Quiero hablar con una persona, por favor" → 1 `pending` handoff with `reason_code='requested_by_contact'`, conversation `human_handoff`, 0 proposals.

## Invariants
- The harness never writes business state outside the scenario `given` hook and the seed; everything the agent does goes through `/internal/messages/inbound` → `/sales-agent/turn` → `/agent-tools/call`.
- Each trial runs on its own cloned database: repetitions cannot contaminate each other; the template is never mutated by a trial.
- Throwaway database names never collide with `CANONICAL_DATABASE_NAMES` and are dropped in `finally`.
- The agent never approves or executes L2/L4: every scenario asserts money/stock untouched and no `agent_proposals`.
- No secret is printed; the real-mode key is read from the environment only.

## Acceptance tests (written first; `tests/test_evals.py`, real PostgreSQL, one pytest process)
1. The 5 scenarios pass `pass^3` in fake mode; `main(["--mode","fake","--k","3"])` returns 0.
2. A scenario with a deliberately wrong assertion (expects 2 pending proposals for the booking conversation) → `main(…, scenarios=[wrong])` returns 1 and the report names the failing check.
3. A check that raises counts as a failed trial (the runner does not crash, exit non-zero).
4. `--write-baseline` writes the JSON shape above; the committed `evals/baselines/fake-pass3.json` matches the current fake-mode result (5/5 scenarios, `pass_k == 1.0`).
5. Real mode without a key returns exit 2 before creating any database.
6. Isolation: after a suite run, no `odontoflow_eval_%` database remains on the server.
