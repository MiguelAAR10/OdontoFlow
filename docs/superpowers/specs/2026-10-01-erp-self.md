## Telos
A patient books from the phone without AIRY answering, and no-shows drop because a fixed D-1 reminder goes out through the sandbox channel.

## Hypothesis of value
Everything needed exists: the slot engine and booking core (`_availability_inputs` `app/scheduling/service.py:146`, `generate_slots`, `_book_appointment_core` :336), `run_idempotent_command` (`app/idempotency/service.py:237`), `_emit_appointment_event` (:600), the run runtime (`app/agents_runtime/service.py:120-229`) and `enqueue_outbound_message` (`app/messaging/service.py:340`, advisory-locked, dedupes on `(org, idempotency_key)`). Missing: one public command that composes them for an anonymous patient behind the BFF credential, and one SQL sweep that enqueues a template. No LLM, no scheduler, no OTP.

## Observable metric
Demo: BFF books → 201 `confirmed` with `reference`; same key resent → same appointment, `Idempotent-Replay: true`, 1 row. Booking for tomorrow with the phone of the seeded sandbox contact → `POST /agent-runs {agent_key:"confirmaciones"}` run 1 `proposed=1` (= queued), `skipped` = tomorrow's appointments without a reachable conversation; run 2 → `proposed=0, deduped=1`; `scripts/sandbox_dispatcher.py` delivers the 1 `outbound_messages` row.

## Contract
**Profile** `patient-booking` (`scripts/issue_credential.py` `PROFILE_PERMISSIONS`, **integration type only**: `profile_matches_type('patient-booking', 'agent')` is false, so it cannot be issued to an agent principal): `services.read, locations.read, practitioners.read, availability.read, appointments.create`. Nothing else (no `patients.*`, `charges.*`, `leads.read`, `appointments.read`, conversations, deliveries).

**`POST /public/bookings`** (scheduling router, already in the `authenticated` loop of `app/__init__.py`, so no factory change; Bearer = BFF credential; `Idempotency-Key` UUIDv4 required for integration/agent by `run_idempotent_command`). **Key contract:** all patients share one BFF principal and receipts are keyed `(org, 'public_booking.create', key)`, so the BFF MUST mint a fresh UUIDv4 per submit (reuse only for a retry of the same submit); a colliding key with another body is `IDEMPOTENCY_KEY_REUSED`, and with the same body replays that booking's reference. Body `PublicBookingCreate` (`extra="forbid"`): `service_id:int`, `location_id:int`, `practitioner_id:int|None`, `start:AwareDatetime`, `full_name:str` (strip, 1..255), `phone:str` pattern `^\+[1-9][0-9]{7,14}$`. No duration/end/state/lead/patient fields. `operation_name="public_booking.create"`, params = body (start ISO-UTC). Service `book_public(session, *, ctx, ..., idempotency)` in `app/scheduling/public_booking.py` (also defines `APPOINTMENT_BOOKED_BY_PATIENT = "appointment.booked_by_patient"` — `app/events/types.py` is outside the write surface; `domain_events.event_type` has no CHECK). `ctx.principal_type != 'integration'` → 403 `PERMISSION_DENIED` before any write (an agent could otherwise skip the L3 patient confirmation that `contact_appointments.book` enforces with confirmation tokens). One transaction, order: `claim_receipt` → `require_permission(appointments.create, location_id)` → `start_utc <= now()` → 422 `INVALID_INPUT` "in the past" (neither `generate_slots` nor `_book_appointment_core` knows about now) → `pg_advisory_xact_lock(hashtextextended('public_booking:'||phone, org))` → **resolve the lead** (no insert yet): `contact_identities.lead_id` of the latest identity with `normalized_phone_e164 = phone` and a lead (org-scoped), else the latest `leads` row with `contact_phone = phone` → **rate limit**: count org appointments created in the last 24 h with `a.lead_id = resolved_lead_id OR ld.contact_phone = phone` (an identity-only match, e.g. an email-only lead, still counts); ≥ `PUBLIC_BOOKING_MAX_PER_PHONE_24H = 3` → 429 → load active service/location (404/409 as today) → **candidate practitioners**: a given `practitioner_id` runs `_load_active_member` (other org/unknown → 404, inactive → 409) + `_require_capability` (→ 409 `CAPABILITY_MISSING`) *before* the slot is classified; omitted → active capable members (`list_eligible_practitioners`, ordered by id), none → 409 `CAPABILITY_MISSING` → **classify the slot**: per candidate `generate_slots(rules, blocks, [], ...)`; `start` absent from every rules-only grid (off-grid, outside hours, blocked) → 422 `INVALID_INPUT` "outside availability"; then the first candidate whose grid *with* confirmed appointments contains it, none → 409 `SLOT_BLOCKED` → **lead**: the resolved one, else insert `Lead(full_name, contact_phone=phone, acquisition_source='direct', service_need_id=service_id)`; no contact identity is created (no consent at booking) → `_book_appointment_core` (re-validates; writes `appointment.created` audit) → `_emit_appointment_event(..., APPOINTMENT_BOOKED_BY_PATIENT)` (payload has ids/times only, no name/phone) → `settle_receipt` with `_appointment_outcome` + `reference`. A concurrent loser on the GiST raises 23P01 → 409 `APPOINTMENT_CONFLICT` (global handler); router wraps with `book_appointment_with_retry` like `POST /appointments`. Replay → 201 from the stored outcome, header `Idempotent-Replay: true`, no second count/insert.
**Known limit (data matching):** lead reuse and the reminder phone match are exact equality on E.164. `_normalize_phone` (`app/commercial/service.py`) only strips non-digits, so a staff-typed lead `999888777` (no `+51`) is never matched; acceptable for the demo, tests seed leads in E.164.
Response 201 `PublicBookingRead`: `reference` (`"OF-" + appointment_id`), `appointment_id`, `state:"confirmed"`, `service_id`, `location_id`, `practitioner_id`, `start_utc`, `end_utc`. The patient is the confirming party (L3 by the patient, not by an agent): no proposal row.
```json
{"reference":"OF-412","appointment_id":412,"state":"confirmed","service_id":3,"location_id":1,
 "practitioner_id":2,"start_utc":"2026-10-02T15:00:00Z","end_utc":"2026-10-02T15:30:00Z"}
```
**Errors:** `INVALID_INPUT` 422 (schema, outside availability, past start, missing/invalid key); `NOT_FOUND` 404 (service/location/practitioner of another org or unknown); `ENTITY_INACTIVE`/`CAPABILITY_MISSING` 409 (given practitioner not capable, or no capable practitioner at all); `SLOT_BLOCKED` 409 (taken); `APPOINTMENT_CONFLICT` 409 (race); `IDEMPOTENCY_KEY_REUSED` 409; `PUBLIC_BOOKING_RATE_LIMITED` 429 `details={"limit":3,"window_hours":24}` (local `PublicBookingErrorCode`, built like `ProposalErrorCode` `app/proposals/errors.py`); `PERMISSION_DENIED` 403 (missing permission, or a non-integration principal).

**`POST /agent-runs {agent_key:"confirmaciones"}`** — `AgentRunCreate.agent_key` / `AgentRunOut.agent_key` Literals widened. `start_run` dispatches on `agent_key` **before** authorizing, so confirmaciones never goes through the cobranza `_authorize` (proposals + charges.read). Gate: the caller is a **human** principal holding `appointments.read` + `deliveries.create` (secretaria and administrador do); agent/integration/system → 403 even with both codes (lean value: a person triggers every patient-visible message). Kill switch env `AGENT_CONFIRMACIONES_ENABLED` (default true, `_boolean_env`) → 409 `AGENT_DISABLED reason=disabled`. tx1 identical to cobranza (claim → authorize → switch → insert `running` → audit `agent_run.started` → settle). No proposer: L1 template, the message is queued **as the caller** (audit `outbound.queued` actor = caller). Counts reuse the columns: `candidates` = selected, `proposed` = newly queued, `deduped` = already reminded, `skipped` = no reachable conversation.
**Select** (one query, own read tx, org-scoped): `appointments a` ⋈ `locations l` ⋈ `services s` ⋈ `leads ld` ⟕ `patients p`, `WHERE a.state='confirmed' AND (a.start_utc AT TIME ZONE l.timezone)::date = (now() AT TIME ZONE l.timezone)::date + 1 ORDER BY a.start_utc, a.id LIMIT 200`, plus LATERAL latest non-closed conversation of a contact identity of the same org with `consent_status <> 'opted_out'` and (`ci.lead_id = a.lead_id` OR `ci.patient_id = a.patient_id` OR `ci.normalized_phone_e164 = ld.contact_phone`), ordered `last_message_at DESC, id DESC`.
**Per candidate**: no conversation → `skipped`. Else `enqueue_outbound_message(conversation_id, text, idempotency_key=reminder_key(org, appointment_id, start_utc), ctx=caller)`, where `reminder_key = str(UUID(bytes=sha256(f"reminder_d1:{org}:{id}:{start_utc_iso}")[:16], version=4))` (deterministic, satisfies `ck_outbound_messages_idempotency_uuid4`; `start_utc` in the key so a rescheduled appointment — same id, new start — gets its own reminder). `duplicate=True` → `deduped`; `IDEMPOTENCY_KEY_REUSED` (same appointment and start, but the conversation or the rendered text changed since the first reminder) → `deduped` too (that start was already reminded); `NOT_FOUND`/`ENTITY_INACTIVE` (closed meanwhile) → `skipped`; anything else → run `failed`. Final tx as COB (`agent_run.completed` audit + domain event). Each enqueue commits its own transaction, so a mid-sweep failure leaves the run `failed` with counts 0 while some reminders are already queued: **a failed run's counts are not authoritative**; the rerun dedupes them (test 9).
**Privacy residual (accepted, follows from no OTP):** the conversation can be matched by phone alone (`ci.normalized_phone_e164 = ld.contact_phone`) even when that identity belongs to another lead/patient, so someone who knows a phone with an open conversation can make the clinic send up to 3 reminders a day (naming the service) to it. Mitigated only by the per-phone rate limit and the human trigger.
**Template** (pure): `"Hola {first_name}, le recordamos su cita de {service_name} mañana {dd/mm/yyyy} a las {HH:MM} en {location_name}. Si no puede asistir, responda este mensaje para reprogramar. ¡Gracias!"`, `first_name` = first token of patient name else lead name; times in the location timezone.

## Invariants (PostgreSQL enforces)
- GiST `EXCLUDE (practitioner_id =, tstzrange &&) WHERE state='confirmed'`: two patients never hold the same slot; composite FKs `(org, lead_id)`, `(org, service_id)`, `(org, location_id)` on appointments make a cross-tenant booking impossible.
- `idempotency_receipts` UNIQUE `(org, operation, key)`: a double submit yields one appointment; receipt commits atomically with appointment, audit and domain event.
- `ck_leads_at_least_one_contact`, `ck_leads_acquisition_source` hold for the created lead.
- At most one reminder per appointment: `uq_outbound_messages_organization_idempotency` on the derived key (+ the enqueue advisory lock); cancelled appointments are excluded by `state='confirmed'`.
- `ck_agent_runs_agent_key IN ('cobranza','reception','confirmaciones')` (0024; down restores 0023's set); existing COB/reception CHECKs unchanged. Audit/domain events atomic via `record_event`/`record_domain_event`.
