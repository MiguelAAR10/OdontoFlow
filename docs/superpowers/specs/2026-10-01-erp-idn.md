## Telos
The UI shows modules by role, and the audit trail names the **person** who approved. Today the only staff credential is
`reception-staff-demo`, an `integration` principal (`scripts/issue_credential.py:130-165`). It cannot pass
`_require_human_reviewer` (`app/scheduling/router.py:406`) or `_require_human_principal` (`app/economics/service.py:1048`).

## Hypothesis of value
The auth path already carries humans. `integration_credentials` binds any principal through its membership
(`app/iam/credentials.py:124-130`). `require_authenticated_context` copies `principals.type` into the ctx
(`app/context.py:198-200`). So two human principals, each with their own credential and a closed role, plus one self-read
route, unlock demo moment 3 (approve with identity) and the per-role shell. No login, no change to `app/context.py`, no migration.

## Observable metric
With Lucía's token, `POST /scheduling/appointment-proposals/confirm` → 200 and `audit_events.actor_id` is her principal id;
Carlos reverses a payment (200), Lucía gets 403; the UI hides modules from `GET /me` permissions alone.

## Cut criteria
Stop and re-plan if a human profile needs a code missing from `app/iam/permissions.py:19-72` (that forces migration 0021,
reserved for B2), if `/me` needs more than `effective_permission_codes` (`app/iam/service.py:150`) plus one role query, or if
`reception-staff-demo`, `conversation-agent` or `sales-agent-v0` change behaviour.

## Contract
**Profiles.** These live in `scripts/issue_credential.py` as `HUMAN_PROFILE_PERMISSIONS`, kept separate from
`PROFILE_PERMISSIONS`. There are no new codes and no migration. Head stays `0020`.
- `secretaria` is an **explicit tuple** (never derived from `reception-staff-demo`, so a later change to the integration
  profile cannot silently change a human role): patients.read/create, appointments.read/create/cancel/reschedule/
  record_outcome, visits.read/create, executions.read/create, leads.read/create, locations/services/practitioners/
  availability.read, charges.read/create, payments.read/create/manage, follow_ups.read/create/manage, waitlist.read/manage,
  conversations.read, contact_appointments.book. That covers agenda, patients, the till, waitlist, chat reads and approving
  appointment proposals. Collection reminders are approved via `follow_ups.*`; `proposals.decide` arrives with B2.
  It never holds payments.reverse, products.*, movements.*, reorder_points.manage.
- `administrador` = `secretaria` + products.read/create, movements.read/create, reorder_points.manage, payments.reverse.
  Transfers and purchases (entries) are approved through `movements.create`. Reports are reads already covered.
- Role codes are **prefixed** like integration roles so a tenant-created `secretaria` role is never overwritten by the
  reconciliation in `_assign_profile` (it deletes and rewrites the role's `role_permissions` by code):
  `staff-secretaria` / `staff-administrador`, names `Secretaria` / `Administrador`. Integration/agent profiles keep
  `integration-<profile>` and `Integration: <profile>`. The one-role-per-principal guard applies to both.
- `_assign_profile(session, *, organization_id, principal_id, profile)` resolves the profile **type-aware** through one
  helper `profile_role(profile) -> (role_code, role_name, codes)` that looks in `HUMAN_PROFILE_PERMISSIONS` first
  (→ `staff-<profile>`) and otherwise in `PROFILE_PERMISSIONS` (→ `integration-<profile>`); the two dicts share no key.
  Existing callers are unchanged.
- **B2 forward-compat.** B2 extends `HUMAN_PROFILE_PERMISSIONS` (e.g. `proposals.read`/`proposals.decide`) instead of adding
  a second human profile set; re-running the seed or the CLI reconciles existing `staff-*` roles to the new tuple.

**Principal identity.** `_resolve_principal` reuses a principal only **within the organization** for `human`: two people
with the same name in two clinics are two principals, so each tenant's audit names its own person. The global
name fallback stays only for `integration`/`agent` (existing behaviour).

**CLI.** `issue_credential.py issue --type human --profile secretaria|administrador --name "<Persona>"`. `ISSUABLE_TYPES`
becomes (`integration`, `agent`, `human`). `--profile` choices = union of both dicts. The profile must match the type:
`human` with a non-human profile → exit 2; `integration`/`agent` with a human profile → exit 2 (L4: an agent never holds
`payments.reverse`); `system` is never issuable. The token is still shown once (existing CLI contract).

**Seed.** `issue_staff_credential(session, *, organization_id, env_path, include_humans=False)`. Without humans it is
byte-identical to today (one line, `BACKEND_DEMO_TOKEN=`), so `tests/test_seed_demo.py` stays untouched. `main()` with
`--issue-staff-credential` passes `include_humans=True`: it mints the staff credential **and** `Lucía Ramos` (secretaria)
and `Carlos Vega` (administrador) in one transaction, commits **once**, then writes the file **once**:
line 1 `BACKEND_DEMO_TOKEN=ofk_…`, line 2
`BACKEND_DEMO_HUMANS=[{"role":"secretaria","display_name":"Lucía Ramos","token":"ofk_…"},…]` (compact `json.dumps`,
ASCII-escaped, `role` = profile name), opened `O_CREAT|O_TRUNC` at mode 0600. On any failure (e.g. the one-role guard)
the session rolls back, no credential is committed and the file is not touched. stdout prints only variable names.

**Route.** `GET /me` in the new `app/iam/router.py`, mounted in `app/__init__.py` inside the `authenticated` loop. The
handler takes `ctx = Depends(require_authenticated_context)` (cached per request with the router-level dependency), never
`resolve_http_context`, so a mis-mount can never fall back to the `system` principal under `ERP_ANONYMOUS_COMPAT`.
- `response_model=MeRead`, 200. `MeRead` = `{principal: {id, type, display_name}, organization: {id, name},
  roles: [{code, name}], permissions: [str]}`. Read-only: no transaction, no `record_event`, no permission check.
- `roles` come from the **membership for (ctx.organization_id, ctx.principal_id)** and only if it is active, ordered by
  code, distinct. A principal holding memberships in several orgs sees only the credential's org.
- `permissions` = sorted `effective_permission_codes(session, ctx.principal_id, ctx.organization_id)` (org-wide only).
- Errors (existing envelope): 401 `AUTHENTICATION_REQUIRED`, 429 `RATE_LIMITED`, 503 `INTEGRATION_DISABLED`.
- `/me` counts against the credential's **read** rate-limit budget (`app/context.py:167-178`): the BFF should cache it per
  session/page load, not call it on every render.
```json
{"principal":{"id":42,"type":"human","display_name":"Lucía Ramos"},
 "organization":{"id":1,"name":"ODONTO SMART"},
 "roles":[{"code":"staff-secretaria","name":"Secretaria"}],
 "permissions":["appointments.cancel","appointments.create","…","waitlist.manage"]}
```

**Idempotency for humans.** `KEY_REQUIRED_PRINCIPAL_TYPES` stays (`agent`, `integration`): a human key is optional. When
the BFF switches from `reception-staff-demo` to the persona tokens it **keeps sending `Idempotency-Key`** on every mutation,
so a retried payment still replays instead of posting twice (plan §2 principle 8). No code change.

## Invariants (PostgreSQL enforces)
- `ck_principals_type` keeps the principal type in the closed set. The type comes from the row, never from input (PR4).
- `fk_integration_credentials_membership` (org, principal) → memberships: a credential cannot exist outside its tenant.
- `role_assignments` composite FKs (`app/iam/models.py:225-243`) keep membership, role and location in one organization.
- `uq_roles_organization_code`: one `secretaria` / `administrador` role per org; `uq_permissions_code`: closed catalog.
- L4 stays in code before any read (`_require_human_principal` / `_require_human_reviewer`), then `require_permission` in DB.

## Acceptance tests (written first, `tests/test_human_identity*.py`, real PostgreSQL)
1. `GET /me` without a token → 401 envelope; revoked token → 401.
2. `GET /me` as Lucía → type `human`, role `staff-secretaria`, and explicitly permissions ⊇ {contact_appointments.book,
   conversations.read, appointments.create, payments.manage, follow_ups.manage} and ∩ {payments.reverse, products.read,
   products.create, movements.read, movements.create, reorder_points.manage} = ∅. Carlos → `staff-administrador`,
   ⊇ Lucía's set + those six codes.
3. `GET /me` as `reception-staff-demo` → type `integration`, role `integration-reception-staff-demo`, unchanged set.
4. An inactive membership → 200 with `roles: []` and `permissions: []`.
5. Lucía confirms a pending appointment proposal → 200; the `appointment_proposal.confirmed` audit row has
   `actor_id == str(lucia.principal_id)` and `actor_type == 'human'`. The integration staff token and an agent token get
   `INVALID_INPUT`.
6. Carlos `POST /payments/{id}/reverse` → 200. Lucía → 403 `PERMISSION_DENIED`. Integration staff and agent tokens →
   `INVALID_INPUT`.
7. Lucía `POST /products/{id}/transfers` → 403. Carlos → 201.
8. Tenant isolation: one principal with roles in orgs A and B calls `/me` with its org-B credential and sees only org-B
   roles/permissions. Carlos-B `POST /payments/{orgA_payment}/reverse` → 404 and confirming an org-A proposal → 404.
9. CLI: human+`reception-staff-demo`, integration+`administrador`, agent+`administrador`, system → each exit 2. The same
   human name in two orgs yields two principals. Integration profiles still get role `integration-<profile>`.
10. Seed (`include_humans=True`): line 1 is `BACKEND_DEMO_TOKEN=ofk_`; `BACKEND_DEMO_HUMANS` parses to two entries whose
    tokens authenticate; mode 0600; no token in stdout; re-running reuses principals and roles. If Lucía already holds
    another role, it raises, commits no credential and writes no file. `main()` passes `include_humans=True`.
11. A human mutation with an `Idempotency-Key` replays and does not duplicate the payment.
12. `test_authorization.py`: both human profiles ⊆ `PERMISSION_CODES`, no agent/integration profile holds
    `payments.reverse`, and the two dicts share no key.
