## Telos
Lucía (secretaria) opens the real chat of a patient and takes over a handoff; everyone sees who did what (AIRY or a human, by name); Carlos (administrador) sees his clinic's productivity in one click.

## Hypothesis of value
The data already exists: `conversations`/`messages`/`reception_handoffs` (`app/messaging/models.py:145,213,398`), audit rows for every mutation with actor (`app/audit/service.py:27`), `agent_proposals`, `agent_runs`. Only the staff-shaped reads are missing — today `/internal/conversations` (`app/messaging/router.py:40,68`) returns bare ids in ascending order for n8n. Reads + one claim + one run row per reception turn make demo moments 1 and 6 visible without new domain logic.

## Observable metric
On the demo seed: `GET /conversations` shows the seeded chat with the patient's name and last-message preview; after one reception turn, `GET /activity` shows `agent_run` (actor_kind `agent`, the reception agent principal's display name) and a human approval by "Lucía …"; `GET /metrics/productivity` equals the hand-computed seed values in the test; secretaria gets 403 on metrics.

## Contract
New `staff_router` in `app/messaging/router.py` (no prefix, mounted in the `authenticated` loop of `app/__init__.py`); new `app/observability/{activity,metrics,runs,router}.py`. All reads: **human principals only** (`principal_type == 'human'`, else 403 `PERMISSION_DENIED` — like `_require_human`, `app/proposals/service.py:297`): `conversation-agent`/`sales-agent-v0` hold `conversations.read` and `collections-agent` holds `proposals.read`, and none of them may list the clinic's chats or audit trail; agents keep their `/internal/*` and tool reads. `ctx.organization_id`-scoped, `require_permission` inside `session.begin()`, `extra="forbid"` query models, `limit` 1..100 (default 25), opaque cursor = urlsafe-b64 JSON of the sort key (B2 `_encode_cursor` pattern); bad cursor/filter → 422 `INVALID_INPUT`. Pages are `{items: [...], next_cursor: str|null}`.

**Display name** (conversations, handoffs): linked patient `full_name` → linked lead `full_name` → masked phone: `+` followed by every E.164 digit masked as `•` except the last 3 (`+51987654123` → `+•••••••••123`). Generic for any country code; the country code is not parsed (no phone library). **Preview**: latest message text truncated to 80 chars; `null` text when `content_redacted_at` is set or `content_expires_at <= now()` (retention job may lag, `app/messaging/service.py:785`). Same rule for message `text`; `media_reference` is never returned. **Conversation `location_id`**: EXISTS an appointment at that location whose `lead_id`/`patient_id` is the contact's (no location column on conversations). `has_media` = `message_type IN ('audio','image')`.

**Cursor guarantee.** Conversations page on `(last_message_at, id) DESC`, and `last_message_at` moves forward on every inbound message (`app/messaging/service.py:253`). Chosen explicitly (an inbox sorted by recency is the product): within one pass, a row whose sort key does not change between pages is never duplicated nor skipped; new conversations and conversations bumped by a new message move *above* the cursor, so they never duplicate, and they appear on the next refresh (a not-yet-seen conversation that is bumped mid-pass is seen on refresh, not in that pass). Messages (`occurred_at, id` ASC), handoffs (`created_at, id` ASC) and activity (`occurred_at, source, id` DESC) page on immutable keys.

**Claimant.** `reception_handoffs` has no claimant column; `claimed_by_principal_id`/`claimed_by_display_name` are derived from `conversations.assigned_principal_id` **only while the handoff `status='claimed'`** (null for `pending`/`resolved`, so a stale assignee left by resume is never shown). The same rule drives the claim's "claimed by someone else" check.

**Claim** (`claim_handoff`, via `run_idempotent_command`, operation `reception_handoff.claim`): one tx — `claim_receipt` → `principal_type == 'human'` + `require_permission(conversations.resume)` (else 403 `PERMISSION_DENIED`) → handoff `FOR UPDATE` (404 if not in org; the tx rolls back, so no audit and no receipt) → `pending` → `claimed`, `conversation.assigned_principal_id = ctx.principal_id`, audit `reception_handoff.claimed` → settle. Already `claimed` with `conversation.assigned_principal_id = ctx.principal_id` → 200 unchanged, no audit; claimed by someone else or `resolved` → 409 `HANDOFF_NOT_PENDING` (module enum like `ProposalErrorCode`, `details={"status"}`). Handing back to AIRY reuses `POST /internal/conversations/{id}/resume` unchanged (`app/agent_tools/reception.py:1303`).

**Activity** = `UNION ALL`, three disjoint branches, all `organization_id = ctx.organization_id`: `audit` = `audit_events` with `entity_type NOT IN ('agent_proposal','appointment_proposal','agent_run')` (COB's `agent_run.*` audit rows are represented by the `agent_run` branch); `proposal` = `audit_events` of `entity_type IN ('agent_proposal','appointment_proposal')`, LEFT JOINed to `agent_proposals` / `appointment_proposals` on `p.organization_id = audit_events.organization_id AND p.id::text = audit_events.entity_id` (gives `agent_key` — `agent_proposals.agent_key`, and `'reception'` for every `appointment_proposal` row — and `location_id`; covers created/approved/declined/executed/confirmed with the real actor); `agent_run` = `agent_runs` rows, `occurred_at = started_at`, `action = 'agent_run.' || status`, actor = `triggered_by_principal_id`, `location_id` null. Actor: `LEFT JOIN principals ON principals.id::text = audit_events.actor_id` (`actor_id` is `String(100)` and holds the literal `'system'` for system rows, so it is never cast to int); `actor_kind` = audit `actor_type` / principal `type` ∈ human|agent|integration|system; display name = `principals.display_name`, `'Sistema'` when no principal matches. `location_id` of an `audit` row: the appointment's location for `entity_type='appointment'`, else null. Filters: `agent_key` keeps only rows whose `agent_key` equals it (so `reception` = reception runs + appointment-proposal rows); `location_id` keeps only rows whose `location_id` equals it — `agent_run` rows and audit rows with no derivable location are dropped; `since` = `occurred_at >= since` (tz-aware, naive → 422). **`summary`** is built only from `action` and the actor display name through a closed Spanish template map (unknown action → the action code); it never reads `before_state`/`after_state`, which can carry patient names, amounts or message-derived data, and the payload carries no state JSON.

**Metrics** (one SQL per block, on the fly, no stored aggregates): `from`/`to` are dates, inclusive, interpreted in each row's location timezone; `from <= to`, span ≤ 92 days, else 422. Appointments: count by `state` of `completed|no_show|cancelled` whose local `start_utc` date is in range. Money (location = execution → visit): `charged` = Σ amount of charges created in range; `collected` = Σ non-reversed payments with local `paid_at` in range; `outstanding` = Σ(amount − `_net_paid_expr`) of charges created in range, as of now (`app/economics/service.py:165`). Proposals per agent (cohort by local `created_at` date in range; location tz, `America/Lima` when the proposal has no location). Both tables expire lazily (no sweep), so counts use the **effective status**: `status='pending' AND expires_at <= now()` counts as expired. `agent_proposals` by `agent_key` — `approved` = `decided_by_principal_id IS NOT NULL AND status <> 'declined'`, `declined` = `status='declined'`, `expired` = `status='expired'` or effectively expired. `appointment_proposals` under `reception` — `approved` = `confirmed`; declining one writes `status='expired'` (`app/agent_tools/booking.py:535`) and only the audit action `appointment_proposal.declined` tells them apart, so `declined` = EXISTS that audit row for the proposal, `expired` = (`status='expired'` and not declined) or effectively expired. Rows for one `agent_key` from both tables are summed; `cobranza` and `reception` are always listed (zeros allowed), others when present, ordered by `agent_key`. `collection_reminders_approved` = approved `collection_reminder` in the cohort.
```json
{"from":"2026-09-01","to":"2026-09-30","location_id":null,
 "appointments":{"completed":18,"no_show":2,"cancelled":3},
 "money":{"currency":"PEN","charged":"2450.00","collected":"1980.00","outstanding":"470.00"},
 "proposals":[{"agent_key":"cobranza","created":4,"approved":2,"declined":1,"expired":0},
              {"agent_key":"reception","created":6,"approved":5,"declined":0,"expired":1}],
 "collection_reminders_approved":2}
```
**Reception turn run.** `sales_agent/api.py` records one row per authorized `/sales-agent/turn` once the outcome is known, on **every** path — runtime returned (`completed`), runtime raised (`failed`, `error_category` = `GatewayError.code`, `agent_unavailable`, `invalid_agent_response`, the runtime diagnostic category, or `unexpected` before re-raising) and the 503 `AGENT_UNAVAILABLE` path where `_build_runtime` fails (`failed`, `agent_unavailable`) — via `app/observability/runs.record_reception_turn(session, ctx, conversation_id, trigger_message_id=latest_inbound_message_id, started_at, finished_at, status, error_category)` in its own tx on the auth sessionmaker: insert `agent_key='reception'`, `trigger='event'`, `conversation_id`, `trigger_message_id`, `triggered_by = ctx.principal_id` (the agent), sweep counts 0 (the card's "counts"; model/tool call counts are **dropped**: `telemetry_sink` is one attribute on the shared cached runtime and FastAPI runs the sync endpoint in a threadpool, so per-request capture would credit counts to the wrong run). Duration = `finished_at − started_at` (finished clamped ≥ started). **No audit row** for reception runs: the feed reads `agent_runs` directly, so an `agent_run.completed` audit row per WhatsApp turn would only bloat `audit_events`. A persistence failure — including an FK/CHECK failure on insert (e.g. a message id that is not in that conversation) — is logged (`sales_agent.runs`, no payload) and swallowed: the turn's response and business effects never depend on it (an error would make n8n retry the turn).

**Errors:** `INVALID_INPUT` 422, `NOT_FOUND` 404, `PERMISSION_DENIED` 403, `HANDOFF_NOT_PENDING` 409, `IDEMPOTENCY_KEY_REUSED` 409.

## Invariants (PostgreSQL enforces)
- 0023: `ck_agent_runs_agent_key IN ('cobranza','reception')`; nullable `conversation_id` + `trigger_message_id` with composite FK `(organization_id, conversation_id, trigger_message_id) → messages(organization_id, conversation_id, id)` RESTRICT (into the existing `uq_messages_organization_conversation_id`), so a run can only cite a message **of that conversation in that org** (MATCH SIMPLE: COB rows leave both null); `ck_agent_runs_reception_trigger`: `agent_key <> 'reception' OR (trigger='event' AND conversation_id IS NOT NULL AND trigger_message_id IS NOT NULL)`. No call-count columns. Existing COB CHECKs keep holding (reception rows are inserted finished; counts 0 = 0). No new index (the feed's `agent_runs` branch uses `ix_agent_runs_org_agent_started`'s leading `organization_id`; audit uses `ix_audit_events_organization`).
- A run cannot name another tenant's principal, nor a message of another conversation or tenant (composite FKs into memberships / messages).
- A claim can only assign a member of the org (`fk_conversations_organization_assignee`); at most one open handoff per conversation (`uq_reception_handoffs_pending_conversation`); claim is serialized by row lock + idempotency receipt.
- Reads add no invariants; audit rows stay atomic with the claim (`record_event`).
