## Telos
A person approves, with one click, what an agent proposed, and the domain command runs **exactly once** under that person's identity (demo moment 3; base for 4 and 5).

## Hypothesis of value
Today only appointment proposals exist, bound to a conversation (`app/scheduling/models.py` `appointment_proposals`). One generic table plus a `kind → executor` registry that re-validates and recalculates lets AIRY Cobranza propose a reminder that Lucía approves from the inbox, and it is reused unchanged by C2/C3. Executors call existing services: `open_follow_up` (`app/economics/service.py:1376`) and `enqueue_outbound_message` (`app/messaging/service.py:321`).

## Observable metric
Approving one `collection_reminder` → exactly 1 `outbound_messages` row, 1 `agent_proposal.executed` audit row with `actor_type='human'` and her principal id, and the proposal is `executed` with `result_ref`. N concurrent approvals → still 1 outbound row. `GET /agent/inbox` shows appointment and agent proposals in one list.

## Cut criteria
Stop and re-plan if an executor needs to open a transaction inside another one (domain services own `session.begin()`), if a change to `app/errors.py`, `app/context.py`, `ExecutionContext` or an existing migration is required, or if the inbox union needs more than one SQL `UNION ALL` plus keyset pagination.

## Contract
**Migration `0021_agent_proposals`** (down 0020; `HEAD_REVISION="0021"`). It adds the permissions `proposals.read`, `proposals.create`, `proposals.decide` (granted to the seeded `system` role, pattern 0020). Table `agent_proposals`:
- `id` Identity; `organization_id` FK; `location_id` NULL, composite FK (org, location_id) → locations; `conversation_id` NULL, composite FK → conversations.
- `agent_key` text (server-derived, see create); `kind` CHECK IN ('collection_reminder','collection_follow_up'), which C2/C3 extend additively; `status` CHECK IN ('pending','approved','executed','failed','declined','expired','superseded').
- `payload` JSONB — exactly `args.model_dump(mode="json", exclude_none=True)` (the normalized args, never the raw body); `payload_hash` CHECK `~ '^[0-9a-f]{64}$'`; `subject_type` / `subject_id` / `subject_version` text; `reason` text 1..500 (Spanish, shown in the UI); `evidence` JSONB (agent-supplied, opaque, never displayed as fact); `dedupe_key` text.
- `execution_key` uuid NOT NULL UNIQUE (v4, server-minted; the domain idempotency key); `proposed_by_principal_id` NOT NULL and `decided_by_principal_id` NULL, both composite FK (org, principal) → `memberships(organization_id, principal_id)`; `decision_note`; `result_ref` JSONB; `error_code`; `correlation_id`; `expires_at`, `created_at`, `updated_at` (timestamptz); UNIQUE(org, id).
- Indexes: `uq_agent_proposals_open_dedupe` UNIQUE (org, dedupe_key) WHERE status IN ('pending','approved'); `ix_agent_proposals_inbox` (org, status, created_at DESC, id DESC).
- No `decided_payload_hash` (it could only ever equal the immutable `payload_hash`).

**Registry** (`app/proposals/executors.py`, `KINDS: dict[str, ProposalKind]`). Each kind declares an args model (`extra="forbid"`), `required_permission`, `ttl` (72 h), and three functions:
- `subject(session, org, args)` → `(subject_type, subject_id, subject_version, location_id, conversation_id)`; raises on create-time problems. Charge lookups are org-scoped (`Charge.organization_id == org`), so another tenant's `charge_id` is `NOT_FOUND`. `location_id` = charge → service_execution → `visit.location_id` (charges have no location column).
- `version(session, org, args)` → the current `subject_version`, never raises (used in tx1).
- `execute(session, ctx_human, proposal)` → `result_ref {type, id}`; raises `AppError` on domain failure.

| kind | args | version | create rejects | permission | execute |
|---|---|---|---|---|---|
| `collection_follow_up` | `{charge_id, next_follow_up_on, note?}` | `f"{net_paid}\|{open_follow_up_id or '-'}"` | balance ≤ 0 → `INVALID_INPUT`; open follow-up exists → `INVALID_INPUT` | `follow_ups.create` | `run_idempotent_command(open_follow_up, operation_name="follow_ups.create", key=str(execution_key))` as the human |
| `collection_reminder` | `{charge_id, message_text 1..1000}` | `f"{net_paid}"` (a follow-up opened meanwhile does **not** supersede a reminder) | balance ≤ 0 → `INVALID_INPUT`; no reachable conversation → `NOT_FOUND` | `deliveries.create` | consent re-check, then `enqueue_outbound_message(proposal.conversation_id, text_body, idempotency_key=str(execution_key), ctx=human)` |

`net_paid` = Σ payments − reversed (`_net_paid_expr`, B0.5). A reachable conversation is the patient's `ContactIdentity` with `consent_status <> 'opted_out'` → `Conversation.status <> 'closed'`, latest `last_message_at`. At execution an opted-out contact → `NOT_FOUND`, a closed conversation → `ENTITY_INACTIVE` (both end as `failed`).
`payload_hash = command_fingerprint(operation=kind, organization_id=org, params=payload)` (sorted keys, compact separators, None omitted). `dedupe_key = f"{kind}:{subject_type}:{subject_id}"`, server-computed.
**L4 invariant:** no kind's `required_permission` is ever `payments.reverse` or `payments.manage` (verify); a test pins it.

**Routes** (`app/proposals/router.py`, prefix `/agent`, mounted in the `authenticated` loop; `response_model` on every route):
| Route | Who | Result |
|---|---|---|
| `POST /agent/proposals` `{kind, payload, reason, evidence?}` + `Idempotency-Key` (UUIDv4) | `principal_type ∈ {agent, integration}` + `proposals.create` | 201 new, 200 when it dedupes onto the open one. A body `agent_key` is rejected (422, `extra="forbid"`). |
| `GET /agent/inbox?status=pending&source=&kind=&location_id=&limit=25(≤100)&cursor=` | `proposals.read`; appointment items only with org-wide `appointments.read` | 200 `{items: [InboxItem], next_cursor}` |
| `GET /agent/proposals/{id}` | `proposals.read` | 200 `InboxItem` |
| `POST /agent/proposals/{id}/approve` `{payload_hash, note?}` + `Idempotency-Key` (UUIDv4) | `human` + `proposals.decide` + the kind's `required_permission` | 200 `InboxItem` with status `executed`, `failed` (+ `error_code`) or `approved` (a same-key replay that arrives while the first call is still executing) |
| `POST /agent/proposals/{id}/decline` `{note?}` | `human` + `proposals.decide` | 200 `declined`; repeating it → 200 same state |

**Create** (`create_proposal`, via `run_idempotent_command(operation_name="agent_proposal.create", params={kind, payload, reason, evidence})`; the key is required because agents and integrations retry — dedupe alone cannot stop a retry after the first proposal was executed or declined from creating a second one):
1. claim receipt → human/system → 403 `PERMISSION_DENIED` → `require_permission(proposals.create)` → `agent_key` = `resolve_agent_key` (agent, B1 registry) or the principal's `display_name` (integration) → `subject()`.
2. In the same transaction, pending rows with this `dedupe_key` and `expires_at <= now` become `expired` (audit `agent_proposal.expired`), so an expired row never holds the dedupe slot.
3. Open row (pending/approved) with the key exists → return it (200). Else insert (201), audit `agent_proposal.created`.
4. Race: an `IntegrityError` whose constraint is exactly `uq_agent_proposals_open_dedupe` (same pattern as `_is_duplicate_follow_up_open`) → rollback, new transaction: re-claim the receipt, re-read the open row, settle, return 200. Any other `23505` is re-raised.
Receipt outcome `{proposal_id, created}`; a same-key replay re-reads the row and keeps the original 201/200.

**Approve** (`approve_proposal` = tx1, via `run_idempotent_command(operation_name="agent_proposal.approve", params={proposal_id, payload_hash, note})`):
1. **tx1**: claim receipt, then in order (any raise rolls back the receipt; the row stays unchanged):
   0. `principal_type != human` → 403; `require_permission(proposals.decide)`; `SELECT … FOR UPDATE` (org-scoped, else 404); `require_permission(kind.required_permission)`.
   1. status ≠ pending → error by status (below).
   2. `expires_at ≤ now` → status `expired` (committed).
   3. hash ≠ stored hash → `PROPOSAL_HASH_MISMATCH` (raise).
   4. `version()` ≠ stored → status `superseded` (committed).
   5. balance ≤ 0 → `INVALID_INPUT` (raise).
   6. Otherwise status `approved`, `decided_by` = human, `decision_note`, audit `agent_proposal.approved`.

   Settle the receipt with outcome `{proposal_id}` and commit.
2. Only on a fresh (non-replayed) call whose row is `approved`: `execute` runs **outside** tx1. The domain service owns its transaction and is idempotent by `execution_key`.
3. **tx3**: `FOR UPDATE`; if still `approved` → `executed` + `result_ref`, or `failed` + `error_code` (the domain `AppError.code`). Audit `agent_proposal.executed|failed` (human actor). No domain events in B2 (the audit rows already carry the outcome; B3's feed adds `proposal.*` events additively).
4. The route re-reads the row and maps: `expired` → 410, `superseded` → 409 `PROPOSAL_SUPERSEDED`; otherwise 200. A same-key replay only re-reads.

**Decline**: human + `proposals.decide`, `FOR UPDATE`. `declined` → 200 same state (no new audit). Pending past `expires_at` → marked `expired` and 410. Any other non-pending status → error by status.

**Error by status** (approve and decline): `expired` → 410 `PROPOSAL_EXPIRED`; `superseded` → 409 `PROPOSAL_SUPERSEDED`; `approved|executed|failed|declined` (decline excepts its own `declined`) → 409 `PROPOSAL_NOT_PENDING` with `details.status`.

**Errors** (existing envelope; `ProposalErrorCode(str, Enum)` in `app/proposals/errors.py`, built with explicit status in the `IamErrorCode` style): `PROPOSAL_HASH_MISMATCH` 409, `PROPOSAL_SUPERSEDED` 409, `PROPOSAL_NOT_PENDING` 409, `PROPOSAL_EXPIRED` 410. Also `PERMISSION_DENIED` 403 (agent/integration approve or decline, human creates), `NOT_FOUND` (also cross-tenant), `INVALID_INPUT`, `IDEMPOTENCY_KEY_REUSED`.

## State machine
```
pending ──approve(tx1)──▶ approved ──tx3──▶ executed
   │                          └────tx3────▶ failed
   ├──approve/decline/create sweep, expires_at ≤ now──▶ expired
   ├──approve, version drift──▶ superseded
   └──decline──▶ declined
```
Terminal: executed, failed, declined, expired, superseded. Only `pending` and `approved` hold the dedupe slot. **Reads never write:** GET and the inbox report a `pending` row past `expires_at` as `expired` (computed), exactly like appointment proposals (`booking.py:318`, `reception.py:148`); the persisted status changes only in approve, decline and the create sweep.

## InboxItem (durable frontend contract)
`source` ∈ agent_proposal | appointment_proposal; `status` is the unified vocabulary pending|approved|executed|failed|declined|expired|superseded. `summary` and `facts` are **computed by the server at read time** (charge amount, net paid, balance, patient); `evidence` is the agent's opaque context and is never the displayed amount. `actions` lists only what this principal may do now (human, pending, and the permissions above).
Appointment items: `kind="appointment_booking"`, `agent_key`/`reason`/`evidence`/`payload_hash`/`facts`/`subject`/`decided_by` null, `payload` = slot details; `conversation_id` and `confirmation_token` are included so the frontend calls the existing `POST /scheduling/appointment-proposals/confirm|decline` with `{conversation_id, confirmation_token}`; their actions are gated on `contact_appointments.book` at the proposal's location. Mapping: `confirmed → executed`, pending past `expires_at → expired`. **Limitation:** an appointment decline is stored as `expired` (`booking.py`, "no new status value"), so appointment items only ever show pending|executed|expired, and `status=declined` never returns them.
Order `created_at DESC, source DESC, id DESC`; the cursor is opaque base64url of `(created_at, source, id)` and one row-value comparison `(created_at, source, id) < cursor` over the `UNION ALL` pages it.
```json
{"source":"agent_proposal","id":812,"kind":"collection_reminder","agent_key":"airy-cobranza","status":"pending",
 "location_id":2,"summary":"Recordatorio de pago a Ana Torres — saldo S/ 120.00","reason":"Saldo vencido hace 9 días",
 "facts":{"charge_id":311,"patient_id":45,"patient_name":"Ana Torres","amount":"150.00","paid":"30.00","balance":"120.00"},
 "evidence":{"days_overdue":9},"payload":{"charge_id":311,"message_text":"Hola Ana, …"},
 "payload_hash":"9f2c…e1","subject":{"type":"charge","id":"311"},"conversation_id":77,"confirmation_token":null,
 "expires_at":"2026-10-04T15:00:00Z","created_at":"2026-10-01T15:00:00Z","decided_by":null,
 "result_ref":null,"error_code":null,"actions":["approve","decline"]}
```
`decided_by` is `{"id": 9, "display_name": "Lucía Ramos"}` once decided.

**Profiles** (`scripts/issue_credential.py`): `secretaria` += proposals.read, proposals.decide, deliveries.create, so she approves collection kinds; `administrador` inherits them and approves every kind (future kinds require `movements.create`). New agent profile `collections-agent` = proposals.create, proposals.read, charges.read, follow_ups.read. No agent or integration profile ever holds `proposals.decide`.

## Invariants (PostgreSQL enforces)
- Kind and status CHECKs close the value domains. `ck_agent_proposals_decided`: status IN (approved, executed, failed, declined) ⇒ `decided_by_principal_id` NOT NULL. `ck_agent_proposals_result`: executed ⇒ `result_ref` NOT NULL. `ck_agent_proposals_error`: failed ⇒ `error_code` NOT NULL. `ck_agent_proposals_expiry`: `expires_at > created_at` (tests that need a past expiry UPDATE both timestamps).
- The partial unique dedupe index allows at most one open proposal per (org, kind, subject). UNIQUE `execution_key` plus `uq_command_receipts_org_operation_key` and `uq_outbound_messages_organization_idempotency` mean the domain effect happens at most once.
- Composite FKs: location, conversation and both principals (via memberships) can never belong to another tenant. All FKs `ondelete=RESTRICT`.
- `FOR UPDATE` in tx1 serializes concurrent approvals: exactly one pending → approved transition.

## Risks
- **Widened error envelope:** four new codes and a 410 outside `app/errors.py`'s enum (same pattern as `PERMISSION_DENIED`). Reported to the lead; promotion into `ErrorCode` is a one-line follow-up for the owner of the error contract.
- **Stuck `approved`:** a crash between tx1 and tx3 leaves the row `approved`; it keeps the dedupe slot, so no new proposal for that subject can be created until it is re-driven. Re-driving is safe (same `execution_key`) but not built in B2.
- **agent_key for new agents:** `resolve_agent_key` maps unknown agent display names to `reception`; a collections agent shows `reception` until B4 (or a one-line `AGENT_KEY_BY_DISPLAY_NAME` entry, outside this card's surface) maps it.
- `created_at = now()` is transaction start; a long transaction could insert behind an issued cursor. Acceptable for an inbox.
