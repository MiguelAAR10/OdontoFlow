## Telos
Collect overdue balances with human approval: the demo inbox shows "debe S/ 180 hace 12 días", Lucía approves, one WhatsApp (sandbox) message is queued under her identity.

## Hypothesis of value
Everything downstream of "an agent proposes" exists (B2: `create_proposal` `app/proposals/service.py:161`, `collection_reminder` kind `app/proposals/executors.py:277-318`, `charge_facts` :85, `normalize_payload`, `_net_paid_expr` `app/economics/service.py:165`). What is missing is the **proposer**: one SQL that picks the work, one fixed Spanish template that drafts, and one persisted run row. No LLM, no scheduler, no runtime: SQL chooses, code drafts, a human decides.

## Observable metric
On the demo seed: run 1 → `proposed = N` (overdue charges whose patient has a reachable conversation; N = 1, the S/ 180 charge), run 2 (same local day) → `proposed = 0, deduped = N`, `skipped` = the overdue charges without a conversation; approving as Lucía → exactly 1 `outbound_messages` row and an `agent_proposal.executed` audit row with her principal; 2 `agent_runs` rows with counts.

## Contract
**Migration `0022_agent_runs`** (down 0021; `HEAD_REVISION="0022"`). Table `agent_runs`: `id` Identity; `organization_id` FK; `agent_key` text CHECK IN ('cobranza') (extended additively by C2/C3); `trigger` CHECK IN ('manual','schedule','event'); `status` CHECK IN ('running','completed','failed'); `triggered_by_principal_id` NOT NULL, composite FK (org, principal) → `memberships(organization_id, principal_id)`; `candidates_count`, `proposed_count`, `deduped_count`, `skipped_count` int NOT NULL default 0, CHECK ≥ 0; `error_category` text NULL; `started_at` timestamptz default now(), `finished_at` NULL; UNIQUE(org, id); index `ix_agent_runs_org_agent_started` (org, agent_key, started_at DESC, id DESC). All FKs RESTRICT. No `correlation_id` column: the `agent_run.started` audit row already carries it. No new permission codes.

**Module `app/agents_runtime/`** (new): `models.py`, `cobranza.py` (select + draft + sweep), `service.py` (`start_run`, `run_agent`, `list_runs`), `schemas.py`, `errors.py` (`AgentRunErrorCode.AGENT_DISABLED` → 409, built like `ProposalErrorCode`, `app/proposals/errors.py`), `router.py` mounted in the `authenticated` loop (`app/__init__.py`). One change in `app/proposals/service.py`: `create_proposal(..., agent_key: str | None = None)` — server-only override (never from an HTTP body: `submit_proposal` never passes it) so rows carry `agent_key='cobranza'`; `resolve_agent_key` would map an unknown agent to `reception`.

| Route | Who | Result |
|---|---|---|
| `POST /agent-runs` `{agent_key:"cobranza"}` (`extra="forbid"`, `Literal`) + `Idempotency-Key` (required UUIDv4 for agent/integration by `run_idempotent_command`, optional for human) | agent/integration with `proposals.create` + `charges.read`, or human with `proposals.decide` + `charges.read` (admin **and** secretaria, see deviation) | 201 `AgentRun`; same-key replay → 201 the same run **as it is now**, header `Idempotent-Replay: true`, no second sweep |
| `GET /agent-runs?agent_key=cobranza&limit=25(≤100)` | `proposals.read` | 200 `{items: [AgentRun]}` newest first, org-scoped; unaffected by the kill switch |

**Idempotency of a run.** The receipt settles in tx1 with `{run_id}`, *before* the sweep. A same-key replay (client retry after a timeout, or a concurrent duplicate) therefore returns the run in whatever status it has now — `running`, `completed` or `failed` (the original call answered 500) — and never sweeps again. Retrying after `failed` needs a **new** key. A replay is resolved on the receipt, before the kill switch, so it still reads an old run while the agent is disabled.

**Kill switch:** env `AGENT_COBRANZA_ENABLED` (default `true`, parsed with `app.config._boolean_env`, read per request in `app/agents_runtime`; `app/config.py` unchanged). `false` → 409 `AGENT_DISABLED` `details={"agent_key":"cobranza","reason":"disabled"}` on both the agent and the human path; no run row, no proposal, no receipt.

**Proposer.** Agent/integration caller → proposals are proposed by the caller. Human caller → proposals are proposed by the org's agent principal named by the **fixed server constant** `COBRANZA_PROPOSER = "airy-cobranza"` (never the body, never the `agent_key` value). Lookup inside tx1: `principals.type='agent' AND display_name='airy-cobranza'` **joined to** `memberships(organization_id=ctx.organization_id, is_active=true)` — agent principals are reused across orgs by name (`scripts/issue_credential.py` `_resolve_principal`), so membership in *this* org is the gate. Then `has_permission(agent, org, proposals.create)`. Missing, inactive membership, member of another org only, or without `proposals.create` → 409 `AGENT_DISABLED` `details={"agent_key":"cobranza","reason":"not_provisioned"}`. The derived `ExecutionContext` keeps the caller's `request_id`/`correlation_id` and is passed **only** to `create_proposal`; it never reaches `approve_proposal` or any executor. The human is recorded only as `triggered_by` (and the run's audit actor); a human never becomes a proposer (B2 `PROPOSER_TYPES` unchanged). `system` principals are refused (403).

**Flow** (`run_agent`):
- **tx1** = `run_idempotent_command(start_run, operation_name="agent_run.start", params={agent_key})`. Order inside the one transaction (AGENTS.md §3.4 — the router runs no read before it): `claim_receipt` → `require_permission` (per principal type) → kill switch → proposer provisioning (human) → insert `running` row (`trigger='manual'`) → audit `agent_run.started` → settle receipt `{run_id}`. Because `claim_receipt` is the first statement, any refusal after it rolls the receipt back with everything else. Replay → re-read the row, return it.
- **Select** (one read, org-scoped, own transaction): charges joined execution → visit → patient → location, `WHERE amount − net_paid > 0 AND (now() AT TIME ZONE loc.tz)::date − (charge.created_at AT TIME ZONE loc.tz)::date ≥ 7` (`OVERDUE_MIN_AGE_DAYS`), `ORDER BY charge.id LIMIT 200`. Net paid is `_net_paid_expr` (payments minus reversed ones) — **not** the seed's `_summary`, which sums gross payments and anchors on Lima. The query also returns `proposed_today` = EXISTS a `collection_reminder` proposal for that charge whose `created_at` falls on today's local date (any status; the card's `collection:charge:<id>:<date>`), plus the last non-reversed payment (`paid_at`, `amount`). `candidates` = all rows.
- **Per candidate**: `proposed_today` → `deduped` (no `create_proposal` call). Else draft, build args/payload through `normalize_payload("collection_reminder", {charge_id, message_text})` (same path as `submit_proposal`, so the stored payload and `payload_hash` are what the inbox shows and approve compares), and call `create_proposal(kind="collection_reminder", idempotency=None, agent_key="cobranza")` directly (its own transaction; `_reminder_subject` already checks reachability). `created` → `proposed`; dedupe onto an open proposal from an earlier day → `deduped`; `AppError` with code `INVALID_INPUT` (paid meanwhile) or `NOT_FOUND` (no reachable conversation / opted out) → `skipped`. **Every other error propagates** to the failed path (e.g. `PERMISSION_DENIED` if the proposer lost `proposals.create` after tx1).
- **Final tx**: `completed`, counts, `finished_at`, audit `agent_run.completed` + `record_domain_event("agent_run.completed", aggregate agent_run, payload=counts)`. Any exception → rollback, new tx marks `failed` + `error_category` (the `AppError` code, else `"unexpected"`) + audit `agent_run.failed`, then re-raise (the error's envelope; 500 for unexpected).

**Draft** (pure function, no Session): `first_name` = first whitespace token of `Patient.full_name`. `message_text = "Hola {first_name}, le escribimos de {location_name}. Tiene un saldo pendiente de S/ {balance} por su atención del {issued_on:%d/%m/%Y}. Puede pagarlo en la sede o responder este mensaje para coordinar. ¡Gracias!"`; `reason = "Saldo vencido de S/ {balance} hace {days_since_issued} días"`; `evidence = {run_id, amount, balance, days_since_issued, issued_on, last_payment_at, last_payment_amount}` (last non-reversed payment or null). `days_since_issued` is the charge's age in local days (overdue starts at 7, so the S/ 180 charge is 12 days old, 5 days overdue); the human text keeps "hace 12 días" per the card. Amounts are server facts, formatted `0.00`.
```json
{"id":7,"agent_key":"cobranza","trigger":"manual","status":"completed","triggered_by_principal_id":12,
 "counts":{"candidates":4,"proposed":1,"deduped":0,"skipped":3},"error_category":null,
 "started_at":"2026-10-01T14:00:00Z","finished_at":"2026-10-01T14:00:01Z"}
```
**Errors:** `AGENT_DISABLED` 409; `PERMISSION_DENIED` 403; `INVALID_INPUT` 422 (unknown `agent_key`, extra field, missing/invalid key for agent/integration); `IDEMPOTENCY_KEY_REUSED` 409.

**Seed** (`scripts/seed_demo.py`, only what the demo needs; direct ORM writes like the existing backdating, no `ingest_inbound_message` — no seeded principal holds `messages.create`): one `sandbox` channel account (`external_account_id="sandbox-local"`, the one `scripts/bootstrap_openrouter_local.py` uses), one `contact_identities` row (`consent_status='opted_in'`, `patient_id` = the S/ 180 patient, `KEY_PAST_VISITS[0]` / patient index 0) and one open `conversations` row for it; **no other patient gets a contact identity**, so N stays 1. Plus the `airy-cobranza` agent principal, member of the org with profile `collections-agent` (via `_resolve_principal` + `_assign_profile`; no credential). Idempotent on rerun.

## Invariants (PostgreSQL enforces)
- CHECKs close `agent_key`, `trigger`, `status`. `ck_agent_runs_finished`: status='running' ⇔ `finished_at` IS NULL; `finished_at ≥ started_at`. `ck_agent_runs_error`: status='failed' ⇔ `error_category` IS NOT NULL. `ck_agent_runs_counts`: status='completed' ⇒ proposed+deduped+skipped = candidates.
- `triggered_by` composite FK into memberships: a run can never name another tenant's principal.
- At most one open proposal per charge: B2's partial unique `uq_agent_proposals_open_dedupe` (`create_proposal` settles a concurrent loser on the winner; B2 tests the race).
- The agent never executes: the sweep calls only `create_proposal`; execution stays B2 approve (human + `proposals.decide` + `deliveries.create`); no L4 code is reachable. At most one outbound per proposal: UNIQUE `execution_key` + `uq_outbound_messages_organization_idempotency`.
- Audit and domain event rows are atomic with the run-row transitions (`record_event`, `record_domain_event`).
