## Telos
No sede runs out of a consumable: the inbox shows "Anestesia: Lince 4 < mín. 10; traspasar 16 desde Jesús María (120, mín. 10)"; the administrador approves and the kardex shows one TRANSFER_OUT/IN pair.

## Hypothesis of value
Stock truth, transfers, reorder points and the approval loop already exist; what is missing is one SQL read that notices the gap, picks the donor and drafts a proposal with the numbers. No LLM: SQL reads, code decides, a human with `movements.create` approves.

## Observable metric
On the demo seed (anestesia: Lince 4 / Jesús María 120 / Magdalena 30, min 10 each): run 1 → `candidates=1, proposed=1`; run 2 same local day → `proposed=0, deduped=1`; approve as Carlos → exactly 2 new `inventory_movements` (same `transfer_id`), Lince 20, Jesús María 104.

## Cut criteria
Stop and re-plan if it needs: a new permission code, a column on `agent_proposals` or `agent_runs`, a change to `create_proposal` beyond COB's `agent_key` override, a change to `transfer_product`/`register_entry`, more than one selection query in the sweep, or touching an existing migration.

## Contract
**Literals (OpenAPI changes).** `AgentKey` (POST body + `GET /agent-runs?agent_key`) and `RunAgentKey` (`AgentRunOut.agent_key`) gain `inventario`; `InboxKind` (`InboxItem.kind`, inbox `kind` filter) gains `inventory_transfer`, `inventory_entry`. `ProposalKindName` (`POST /agent/proposals` body) stays **closed**: only the server-side sweep proposes inventory kinds, so evidence is always server facts (`kind:"inventory_transfer"` → 422).

**Migration 0025** (down 0024): widen `ck_agent_proposals_kind` with `inventory_transfer`, `inventory_entry`, and `ck_agent_runs_agent_key` with `inventario`. ORM mirrors: `PROPOSAL_KINDS` + CHECK in `app/proposals/models.py`, CHECK in `app/agents_runtime/models.py`. Downgrade deletes those rows first and restores the 0024 sets.

**Kinds** (`app/proposals/executors.py`, additive). `ProposalKind` gains `revalidate: Callable[[Session,int,BaseModel], None]`; `approve_proposal` calls `spec.revalidate` instead of the hard-coded `require_open_balance` (collection kinds keep `require_open_balance`). Inventory kinds use a no-op revalidate: any movement that changes a balance also changes the version, so the version check supersedes first; `transfer_product`'s `require_stock` under the product lock is the final floor (failure → `failed`).
Both inventory kinds: `required_permission=MOVEMENTS_CREATE` (administrador only; secretaria lacks it → 403 on approve, inbox `actions == ["decline"]`, decline works), TTL 72h, `subject_type="product_location"`, `subject_id = product_location_subject_id(product_id, location_id)` (single helper in `executors.py`, used by the resolver and the sweep's SQL; `"{product_id}:{location_id}"` of the location that is short), `conversation_id=None`, proposal `location_id` = that location.

| kind | args (`extra="forbid"`) | subject_version | execute (as the approving human) → `result_ref` |
|---|---|---|---|
| `inventory_transfer` | `product_id, origin_location_id, destination_location_id, quantity>0` (origin≠dest) | `"{max_mov_id(origin)}\|{max_mov_id(dest)}"` ("-" if none) | `run_idempotent_command(transfer_product, OP_TRANSFERS_CREATE, key=execution_key, TransferCreate(..., reason="Propuesta #{id}"))` → `{type:"inventory_transfer", id: outcome.outcome["transfer_id"]` on replay else `result.transfer_id}` |
| `inventory_entry` | `product_id, location_id, quantity>0` (no `unit_price`) | `"{max_mov_id(location)}"` | `run_idempotent_command(register_entry, OP_ENTRIES_CREATE, key=execution_key, EntryCreate(location_id, quantity))` → `{type:"inventory_movement", id: int(outcome.outcome["resource_id"])` on replay else `result.id}` |

`max_mov_id` = max `inventory_movements.id` per org×product×location. Subject resolver (create time): product and location(s) org-scoped (else `NOT_FOUND`) and active (else `ENTITY_INACTIVE`, raised explicitly: `_load_product`/`_load_location` do not check it). It does not check origin balance; the sweep's surplus math decides quantity. Any movement at either location after the proposal → version drift → `superseded` (409 `PROPOSAL_SUPERSEDED`), stock unchanged. Summaries: `"Traspaso de {q} uds. (producto #{p}) sede #{o} → #{d}"`, `"Reposición de {q} uds. (producto #{p}) en sede #{l}"`; names live in `reason`/`evidence`.

**Run** `POST /agent-runs {agent_key:"inventario"}` (same route, `Idempotency-Key` rules, replay and failed path as COB). `start_run` gains an `inventario` branch; `run_agent` gains an explicit `inventario` → `inventario.sweep` branch (cobranza stays explicit). The COB `_authorize` and `_proposer` are parameterized (no copy): `_authorize(session, ctx, reads)` — machine caller needs `proposals.create`, human `proposals.decide`, `system` → 403, then every code in `reads` (cobranza `(charges.read,)`, inventario `(products.read, movements.read)` — the sweep reads names/units and the ledger); `_proposer(session, ctx, name=, agent_key=)` — machine caller proposes as itself; human trigger → the fixed constant `INVENTARIO_PROPOSER="airy-inventario"` (agent type + active membership in this org + `proposals.create`), else 409 `AGENT_DISABLED {agent_key:"inventario", reason:"not_provisioned"}`. Kill switch env `AGENT_INVENTARIO_ENABLED` (default true) → 409 `reason=disabled`. New profile `inventory-agent = (proposals.create, proposals.read, products.read, movements.read)`; the seed adds the principal, no credential. Proposals carry `agent_key="inventario"`.

**Sweep** (`app/agents_runtime/inventario.py`). **One** org-scoped read returns **every** `reorder_points` row (active product, active location), no SQL LIMIT, with: product name/unit, location name, signed ledger `balance` (same `case` as `list_low_stock`), `consumption_7d` = Σ SALIDA with `moved_at ≥ now()-7 days`, `max_movement_id`, and `handled` = EXISTS an inventory-kind proposal (either kind) on `product_location_subject_id(product, location)` that was created today (location tz, any status) **or** is open, where open = `status='approved' OR (status='pending' AND expires_at > now())` (an expired-but-unpersisted pending row never holds the subject).
In Python: candidates = rows with `balance < min_quantity`, ordered by (location_id, product_id), capped at `MAX_CANDIDATES=200`; `surplus[product, location] = balance − min` for rows with `balance > min`. Per candidate: `handled` → `deduped`. Else donor = same product, other location, largest *remaining* surplus > 0 (tie → lowest location id). `target_fill = TARGET_MULTIPLIER × min − balance` (`TARGET_MULTIPLIER=2`, coordinator decision: refill to twice the minimum). Donor → `inventory_transfer` with `quantity = min(target_fill, surplus)`, and that donor's surplus is decremented in memory after a created proposal (two short sedes never share the same units in one run); no donor → `inventory_entry` with `quantity = target_fill`. Built through `normalize_payload` + `create_proposal(idempotency=None, agent_key="inventario")`; `created` → `proposed`, dedupe → `deduped`, `INVALID_INPUT`/`NOT_FOUND`/`ENTITY_INACTIVE` → `skipped`, anything else → run `failed`.
Evidence and version come from the same read: evidence carries `subject_version` built from the read's `max_movement_id`s; the resolver re-derives it at create time, and a test pins `evidence.subject_version == proposal.subject_version`. A movement in the milliseconds between the sweep read and `create_proposal` would leave evidence one movement stale (residual, accepted: approval still re-checks the version, and `require_stock` is the floor).
Expected sibling behavior: two transfers drawing on one donor carry the donor's `max_mov_id` in their versions, so approving one supersedes the other; the same-day dedupe (any status) then blocks a re-proposal until the next local day. This is by design (the second sede's numbers changed; tomorrow's run re-plans).
Cross-kind: `dedupe_key` is per kind, so PostgreSQL alone does not prevent an open transfer and an open entry for one product×location; the sweep's `handled` covers both kinds, but two concurrent runs could race and the human would see two items. Accepted, not claimed as a DB invariant.

**Evidence** (server facts, decimals `0.00`): `{run_id, product_id, product_name, unit, subject_version, target:{location_id, name, balance, min_quantity, consumption_7d}, donor:{location_id, name, balance, min_quantity, surplus, consumption_7d}|null, target_fill, quantity}`. `reason = "{product}: {target} {balance} < mín. {min}; traspasar {q} desde {donor} ({donor_balance}, mín. {donor_min})"` or `"{product}: {target} {balance} < mín. {min}; sin sede donante, reponer {q}"`.
```json
{"kind":"inventory_transfer","agent_key":"inventario","payload":{"product_id":3,"origin_location_id":2,"destination_location_id":1,"quantity":"16.00"},
 "evidence":{"run_id":9,"product_id":3,"product_name":"Anestesia lidocaína 2% (cartucho)","unit":"cartucho","subject_version":"14|13",
  "target_fill":"16.00","quantity":"16.00",
  "target":{"location_id":1,"name":"ODONTO SMART Lince","balance":"4.00","min_quantity":"10.00","consumption_7d":"0.00"},
  "donor":{"location_id":2,"name":"ODONTO SMART Jesús María","balance":"120.00","min_quantity":"10.00","surplus":"110.00","consumption_7d":"0.00"}}}
```
**Errors:** `PERMISSION_DENIED` 403; `INVALID_INPUT` 422; `AGENT_DISABLED` 409; `PROPOSAL_SUPERSEDED` 409; `IDEMPOTENCY_KEY_REUSED` 409. No new codes.

## Invariants (PostgreSQL enforces)
- Closed CHECKs on `agent_proposals.kind` and `agent_runs.agent_key`; one open proposal per `dedupe_key` (per kind × subject; `uq_agent_proposals_open_dedupe`).
- One execution per proposal: UNIQUE `execution_key` → PF4 receipt; a transfer is exactly one OUT + one IN (partial uniques + deferred pair trigger); quantity CHECK > 0.
- Tenant: composite FKs movements/reorder_points/proposals → `(organization_id, id)` of products/locations; `triggered_by` → memberships.
- Stock floor: product row `FOR UPDATE` + ledger sum in `require_stock`; audit/domain events atomic with each mutation.
- Agents never execute: the sweep only calls `create_proposal`; `movements.create` is not L4 and no kind requires L4 (pinned test extended).
